Desglose

Desglose por fase

F0 – Base (3 meses, 6 sprints, 2 devs)

Objetivo: Base estable del App editor (export/publicación + layout) y piloto de logs para que el resto de fases no se bloqueen.

  • App editor (Mejoras P0): Export/publicación estable + ZIP; Smart-Adapt en componentes de layout; resize persistente.
  • Logs (Fases 1–2): Logs estructurados JSON con flowId y step en al menos un flujo piloto (ej. análisis ATS o export App editor); persistir por flowId y exponer GET /flows/:flowId/logs.

Entregables: Editor con export fiable y descarga ZIP; flujo de análisis o export con logs exportables por flowId.

F1 – Núcleo y visión en hub (4 meses, 8 sprints, 2–3 devs)

Objetivo: Schema y catálogo consolidados (Visión F1); panel del App editor en el hub; mejoras P1 App editor.

  • Visión F1: Schema de página estable (JSON Schema), registro de componentes como catálogo maquinaable, export estable; opcional API interna.
  • Integración F1: Panel “Sitios (App editor)” en ATS (lista + enlaces a preview/prod); API básica en el editor de lista de proyectos y estado de publicación (o mock).
  • App editor P1: Modo aislado unificado + persistencia; responsive y vista previa móvil.

Entregables: Documentación de schema y catálogo; hub con panel App editor; editor con modo aislado y persistencia.

F2 – API, publicación e integración (6 meses, 12 sprints, 3–4 devs)

Objetivo: API del builder (headless), flujo Publicar con staging/rollback, integración publicar desde hub y quality gate, logs con UI y templates.

  • Visión F2–F3: API REST (páginas, componentes, preview); flujo “Publicar” (versión, export, deploy), preview y staging, rollback, permisos.
  • Integración F2–F3: Botón “Publicar a producción” desde hub (API del App editor); quality gate (métricas ATS/Sonar antes de permitir publicar).
  • Logs F3–F5: UI “Ver logs en vivo” y “Exportar logs del flujo”; tipos de flujo e historial; flujos guardados como templates y re-ejecución desde hub.

Entregables: API del builder operativa; publicación controlada (preview → staging → prod) con rollback; hub con publicar + quality gate; logs en vivo y flujos guardados.

F3 – IA y automatización (6 meses, 12 sprints, 3–4 devs)

Objetivo: IA que genera/modifica apps (desde brief o asistente); integración rollback/auditoría y IA en contexto; logs para IA y tests.

  • Visión F4: Flujo “Generar app desde brief” con IA; adapter IA → acciones; integración con aprobación y publicación.
  • Integración F4–F5: Rollback y auditoría desde hub; estado de sitios (App editor) en contexto Gemini; API headless del editor para IA/automatización.
  • Logs F6–F7: Export de logs como contexto a Gemini (u otro); respuestas en hub (resumen, diagnóstico, sugerencia); flujos como oráculo para tests (re-ejecutar en CI, agente que genera tests desde flujo real).

Entregables: Chat/API que genera o modifica schema desde brief; informes y recomendaciones IA en hub; tests generados o validados desde flujos.

F4 – Producto avanzado (6+ meses, 12+ sprints, 4 devs)

Objetivo: Export enriquecido (imágenes + MD), IAs especializadas por app, bot del cliente (voz/texto, clonable, tareas a agentes, análisis datos/métricas); mejoras P2–P3.

  • Logs F8 (visión): Export enriquecido (imágenes y Markdown en hitos del flujo); IAs especializadas por app; bot del cliente (comandos voz/texto, clonable, dar tareas a agentes, analizar datos y métricas de negocio).
  • App editor P2–P3: Pulido UI (cards, forms, gallery), botón Publicar + flujo premium; tests, CI, documentación y onboarding.

Entregables: Exports de flujo con imágenes y MD; bot por cliente/workspace con voz y orquestación de agentes; producto estable y documentado.

Presupuesto económico (orientativo)

Coste por desarrollador y totales según hipótesis de coste/mes. Ajustar a costes reales (internos, externos, país).

Concepto Coste/mes (€) Notas

Desarrollador mid (referencia interna)3.500 – 5.000Bruto empresa, España
Externalizado (agencia / freelance)6.000 – 12.000Por dev/mes según perfil y mercado

Ejemplo de cálculo (equipo mixto 2–3 devs, 24 meses)

Hipótesis: 2 devs × 24 meses (promedio 2,5 devs equivalentes) = 60 dev·mes. A 5.000 €/dev·mes → 300.000 € en personal de desarrollo (solo referencia; no incluye infra, herramientas, gestión de producto, diseño, etc.).

Si F0–F2 se hacen con 2 devs (13 meses) y F2–F4 con 3–4 devs (11 meses): (2×13 + 3,5×11) = 26 + 38,5 = 64,5 dev·mes → ~322.000 € a 5.000 €/dev·mes.

Incluir además: infraestructura (hosting, CI, APIs de IA), licencias (Sonar, etc.), posible diseño UX/UI y gestión de producto si no están cubiertos por el mismo equipo.

Riesgos

Hipótesis y riesgos

  • Sprint de 2 semanas: Asumido como estándar; equipos que usen 1 o 3 semanas deben recalcular el número de sprints por fase.
  • Paralelismo: App editor, ATS, integración y logs pueden repartirse entre devs; los plazos pueden acortarse si el equipo trabaja en paralelo sin bloqueos.
  • Priorización: Si se recorta alcance (ej. solo integración básica sin IA avanzada), F3–F4 se reducen; si se prioriza bot y export enriquecido antes que “Generar app desde brief”, el orden de ítems dentro de F3–F4 puede cambiar.
  • Dependencias: F2 depende de F0–F1 (export estable, panel en hub); F3 depende de API builder y logs F1–F5. Retrasos en F0–F1 impactan el resto.
  • Riesgo de alcance: Añadir funcionalidades no previstas en los docs (nuevas apps, integraciones) aumenta duración y/o equipo.

Este presupuesto debe revisarse con responsables de producto y técnicos; los documentos en ideas/ y ideas/profundizar/ son la fuente de verdad del alcance.
